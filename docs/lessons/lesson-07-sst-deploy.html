Lesson 7: AWS への初回デプロイ

SST / OpenNext / Aurora Serverless v2 ｜ 目安 Day 22–24（約 3 時間）＝ 既知の山場その 2

ゴール

ここまでのアプリ（認証＋CRUD＋タグ）が、CloudFront の URL で Aurora を DB として動いている状態。

先に知っておくコストの話

リソースコスト感
Lambda + CloudFront + S3低トラフィックならほぼ無料枠内
Aurora（0 ACU〜、auto-pause）停止中の計算コスト 0。ストレージ課金は継続（月 $1〜数ドル）
VPC の NATnat: "ec2"（t4g.nano）で月 $3〜4 程度。マネージド NAT Gateway（月 $30〜）は選ばない

遊び終わったら pnpm dlx sst remove で全リソースを削除できます（これも IaC の学びの一部）。

Day 22: SST の初期化と構成

AWS Profile の設定が必要です

このプロジェクトでは AWS Profile braindump を使います。SST CLI には --profile フラグがないため、sst.config.ts の providers.aws.profile で指定します（後述）。

また、~/.aws/config が SSO ベースの設定の場合、初回および SSO セッション期限切れ時に下記コマンドでログインが必要です：

aws sso login --profile braindump

ログイン後、接続確認：

aws sts get-caller-identity --profile braindump

正しく設定されていれば Account ID と ARN が表示されます。

1. 初期化

pnpm dlx sst@latest init

Next.js プロジェクトを自動検出し、sst.config.ts が生成されます。

2. sst.config.ts を書く

/// <reference path="./.sst/platform/config.d.ts" />

export default $config({
  app(input) {
    return {
      name: "braindump-todo",
      removal: input?.stage === "production" ? "retain" : "remove",
      home: "aws",
      providers: {
        aws: { profile: "braindump" },
      },
    };
  },
  async run() {
    const vpc = new sst.aws.Vpc("Vpc", { bastion: true, nat: "ec2" });

    const database = new sst.aws.Aurora("Database", {
      engine: "postgres",
      vpc,
      scaling: { min: "0 ACU", max: "4 ACU" },
    });

    const openaiApiKey = new sst.Secret("OpenaiApiKey");

    new sst.aws.Nextjs("Web", {
      vpc,
      link: [database, openaiApiKey],
    });
  },
});

学びどころ：SST v3 の 3 つの中心概念

  • コンポーネント — sst.aws.Aurora は「クラスタ＋サブネットグループ＋セキュリティグループ…」を 1 つにまとめた高水準部品。scaling.min: "0 ACU" で auto-pause が有効になる（requirements.md の決定事項どおり）。
  • link — リソース間の配線。link: [database] と書くだけで、接続情報が Lambda に注入され、かつ必要な IAM 権限とネットワーク設定が付与される。環境変数を手でコピペする世界からの脱却。
  • Secret — pnpm dlx sst secret set OpenaiApiKey sk-... --stage dev で登録し、コードから Resource 経由で読む。secret はステージごとに登録する（--stage を省略すると personal ステージに入ってしまい、dev ステージのアプリからは読めない）。.env をデプロイ先に持ち込まない。

3. アプリ側から接続情報を読む

src/db/index.ts を、link された Aurora とローカル Docker の両対応にします：

import { drizzle } from "drizzle-orm/node-postgres";
import { Pool } from "pg";
// Next.js 16（ESM / Turbopack）では require ではなく import で読む。
// Resource は遅延評価の proxy なので、ローカルで触らなければ副作用はない。
import { Resource } from "sst";
import * as authSchema from "./auth-schema";
import * as schema from "./schema";

function buildConnectionConfig() {
  if (process.env.DATABASE_URL) {
    const isLocal =
      process.env.DATABASE_URL.includes("localhost") ||
      process.env.DATABASE_URL.includes("127.0.0.1");
    return {
      connectionString: process.env.DATABASE_URL,
      // ローカル Docker 以外（Aurora トンネル経由）は SSL 必須
      ...(isLocal ? {} : { ssl: { rejectUnauthorized: false } }),
    };
  }
  // SST 環境では link された Aurora から取る
  return {
    host: Resource.Database.host,
    port: Resource.Database.port,
    user: Resource.Database.username,
    password: Resource.Database.password,
    database: Resource.Database.database,
    // Aurora は SSL 必須。自己署名証明書のため検証は無効化
    ssl: { rejectUnauthorized: false },
  };
}

const pool = new Pool({ ...buildConnectionConfig(), max: 1 });

export const db = drizzle(pool, {
  schema: { ...schema, ...authSchema },
});

Aurora は SSL 接続が必須

Aurora PostgreSQL は暗号化なしの接続を拒否します（no pg_hba.conf entry for host ... no encryption）。 ssl: { rejectUnauthorized: false } は Aurora が自己署名証明書を使うための設定で、通信自体は暗号化されています。

また、ローカルの .env に書いた DATABASE_URL は SST がビルド時に Lambda 環境へ持ち込んでしまいます。 Lambda 上では Resource.Database を使わせるために、次の手順 6 で DATABASE_URL: "" で上書きします。

学びどころ：Lambda では接続プールを小さく

max: 1 は Lambda の実行モデルに合わせた設定です。Lambda は 1 インスタンス＝同時 1 リクエストなので、 インスタンスごとに大きなプールを持つと、スケール時に Aurora の接続上限を食い潰します。 本格運用では RDS Proxy を挟みますが、トレーニング用途では max: 1 で十分。

Day 23: デプロイとマイグレーション

4. next.config.ts の設定

初回デプロイ時は Resource.Database の型定義がまだ生成されておらず、TypeScript エラーでビルドが止まります。next.config.ts にビルド時の型チェックをスキップする設定を追加します：

const nextConfig: NextConfig = {
  // SSTデプロイ時はResource型がまだ生成されていないためスキップ
  typescript: {
    ignoreBuildErrors: true,
  },
};

なぜ型チェックをスキップするのか

Resource.Database の型は .sst/types.generated.d.ts に生成されますが、このファイルはデプロイが一度完走して初めて作られます。「デプロイに成功しないと型が生成されない、型がないとビルドが通らない」という鶏と卵の問題です。一度デプロイが完走すれば以後は型が存在するためエラーは出なくなります。型チェックはローカル開発（pnpm dev）時に行えば十分です。

5. シークレットの登録とデプロイ

pnpm dlx sst secret set OpenaiApiKey sk-xxxx --stage dev   # 値は Lesson 8 まで仮でも可
pnpm dlx sst deploy --stage dev

初回は 15〜30 分かかります（Aurora クラスタと CloudFront の作成が遅い）。コーヒーを淹れながら、出力されるリソース名を眺めて「何が作られているか」を追ってください。完了すると CloudFront の URL が表示されます。

.next ディレクトリの権限エラーが出る場合

SST のビルドプロセスが .next ディレクトリ内に root 権限のファイルを作ることがあります。 EPERM: operation not permitted, open '.next/trace' というエラーが出たら、.next を削除してからデプロイしてください：

sudo rm -rf ./.next && pnpm dlx sst deploy --stage dev

繰り返し発生するのを防ぐため、package.json にデプロイ用スクリプトを追加しておくと便利です：

"deploy": "rm -rf ./.next && pnpm dlx sst deploy --stage dev"

以降は pnpm deploy だけで済みます（rm -rf は相対パスのため安全）。

Vpc コンポーネントのバージョン不一致エラーが出る場合

途中で失敗したデプロイの状態が残っていると、SST のバージョンアップによって Vpc コンポーネントのバージョンが合わなくなることがあります：

There is a new version of "Vpc" that has breaking changes.
To continue using the previous version, rename "Vpc" to "Vpc.v1".

エラーの指示どおり sst.config.ts 内の "Vpc" を "Vpc.v1" にリネームして再実行してください。SST が状態ファイルと一致させてくれます。

6. Aurora へのマイグレーション

Aurora は VPC 内にいるため、手元からは直接届きません。sst.config.ts の bastion: true がここで効きます：

pnpm dlx sst tunnel --stage dev

初回実行時に Make sure you have installed the tunnel with sudo sst tunnel install と表示されたら、別ターミナルで先にインストールしてください：

sudo pnpm dlx sst tunnel install

トンネルが Waiting for connections... と表示されたら準備完了です。Aurora の接続情報を取得します（別ターミナルで）：

pnpm dlx sst shell --stage dev node -e "const {Resource}=require('sst');const d=Resource.Database;console.log('postgres://'+d.username+':'+d.password+'@'+d.host+':'+d.port+'/'+d.database)"

表示された URL を使ってマイグレーションを実行します。Aurora は SSL 必須のため NODE_TLS_REJECT_UNAUTHORIZED=0 と ?sslmode=require が必要です：

NODE_TLS_REJECT_UNAUTHORIZED=0 \
DATABASE_URL="postgres://postgres:パスワード@ホスト:5432/braindump_todo?sslmode=require" \
pnpm exec drizzle-kit migrate

学びどころ：マイグレーションファイル方式がここで報われる

Lesson 2 で push ではなく generate → migrate を選んだ理由がこれです。drizzle/ に積んだ SQL ファイルの列を そのまま Aurora に適用すれば、ローカルとまったく同じスキーマが再現されます。「DB が 2 つになった瞬間、 マイグレーションは履歴で管理するしかなくなる」ことを体感してください。

7. Better Auth の URL 設定と再デプロイ

デプロイ先の URL を Better Auth に教える必要があります。また、ローカルの .env にある DATABASE_URL（Docker の localhost を指す値）が Lambda 環境に持ち込まれないよう空文字で上書きします。sst.config.ts の Nextjs コンポーネントを更新してください：

new sst.aws.Nextjs("Web", {
  vpc,
  link: [database, openaiApiKey],
  environment: {
    BETTER_AUTH_URL: "https://（CloudFront の URL）",
    BETTER_AUTH_SECRET: process.env.BETTER_AUTH_SECRET!,
    // ローカルの DATABASE_URL を Lambda に持ち込まない（Resource.Database を使わせる）
    DATABASE_URL: "",
  },
});

process.env.BETTER_AUTH_SECRET は sst.config.ts の実行時に .env から読まれます——SST は .env を自動ロードします。URL は初回デプロイ後に判明するので、2 回目のデプロイで設定する流れで OK。

更新後に再デプロイします：

pnpm deploy

8. ユーザーの事前登録

認証は招待制のため、Aurora に初期ユーザーを登録する必要があります。トンネルを開いたまま、scripts/seed-users.ts のメールアドレスとパスワードを自分のものに書き換えてから実行してください：

NODE_TLS_REJECT_UNAUTHORIZED=0 \
BETTER_AUTH_DISABLE_SIGNUP=false \
DATABASE_URL="postgres://postgres:パスワード@ホスト:5432/braindump_todo?sslmode=require" \
pnpm exec tsx scripts/seed-users.ts

Registered: あなたのメールアドレス と表示されれば成功です。

Day 24: 動作確認と後片付けの練習

9. 本番相当での動作確認

CloudFront URL でサインアップ〜todo 作成〜タグ付けまで一通り実行します。

Aurora のコールドスタートを「観測」する

しばらく（デフォルトでは非アクティブ数分〜）放置すると Aurora は auto-pause します。 その状態で最初のリクエストを送ると十数秒待たされるはず——これは requirements.md で許容済みの想定挙動です。 ただし Server Action がタイムアウトする場合があるので、体感しておくこと。リロードで復帰します。 「初回だけ遅い」を実際に観測することが、このアーキテクチャを選んだ判断の意味を理解する近道です。

10. sst dev を知っておく（実行は任意）

sst dev は「インフラは AWS 上の実物、Next.js は手元で実行」というハイブリッドな開発モードで、link されたリソース（Aurora、Secret）に手元のコードから Resource でアクセスできます。ただし今回の構成では 2 つ注意があります：

  • ステージ指定なしの pnpm dlx sst dev は personal ステージ（ユーザー名）に別スタックを新規作成します。VPC と Aurora クラスタがもう 1 組でき、課金も増えます。かといってデプロイ済みの dev ステージと sst dev を同一ステージで共用するのも非推奨です。
  • 手順 3 の buildConnectionConfig() は DATABASE_URL を優先するため、.env に DATABASE_URL がある限り、sst dev で起動しても接続先は Docker Postgres のままです。

したがって Lesson 8〜9 の開発は Docker Postgres 相手の pnpm dev で進めます。sst dev を試すのは自由ですが、終わったら personal ステージのリソースを pnpm dlx sst remove で必ず片付けてください。

チェックポイント

  • CloudFront URL でアプリ全機能が動く
  • Aurora が auto-pause → 再開する挙動を観測した
  • AWS コンソールの Billing で課金状況を一度確認した
  • sst.config.ts の各行が何を作っているか説明できる

つまずきポイント（山場その 2 の核心）

  • デプロイ失敗時は慌てて remove しない — SST は Pulumi ベースで状態管理しているため、失敗しても再実行すれば途中から続きをやってくれる（冪等）。まずエラーメッセージのリソース名を読む。
  • SSO セッション切れ — failed to refresh cached credentials が出たら aws sso login --profile braindump を実行してから再試行。SSO トークンは数時間〜1日で期限切れになる。
  • SST プラグインの権限エラー — mkdir /Library/Application Support/sst/plugins: permission denied が出たら sudo chown -R $USER "/Library/Application Support/sst/" で所有権を修正する。
  • .next ディレクトリの権限エラー — EPERM: operation not permitted, open '.next/trace' が出たら sudo rm -rf ./.next してからデプロイし直す。pnpm deploy スクリプトを使えば毎回自動でクリアされる。
  • Vpc コンポーネントのバージョン不一致 — 途中失敗した状態が残っていると SST のバージョンアップ後に不一致が起きる。エラーに従って "Vpc" を "Vpc.v1" にリネームして再実行。
  • TypeScript エラーでビルドが止まる — Property 'Database' does not exist on type 'Resource' は初回デプロイ前に必ず出る。next.config.ts に typescript: { ignoreBuildErrors: true } を追加する。
  • Lambda が localhost:5432 に接続しようとする — ローカルの .env の DATABASE_URL が Lambda 環境に持ち込まれることで起きる。sst.config.ts の environment に DATABASE_URL: "" を追加して上書きする。
  • Aurora への接続で SSL エラー — Aurora は SSL 必須。src/db/index.ts に ssl: { rejectUnauthorized: false } を追加する。tunnel 経由のコマンド（migrate・seed）にも NODE_TLS_REJECT_UNAUTHORIZED=0 と ?sslmode=require が必要。
  • Lambda から DB に届かない（接続タイムアウト） — Nextjs コンポーネントに vpc を渡し忘れているのが定番。
  • 認証だけ壊れる — BETTER_AUTH_URL が CloudFront の URL と一致しているか確認。Cookie の secure 属性まわりも疑う。
  • ハマったら 30 分で切り上げる — SST の Discord／GitHub Discussions を検索する。初回デプロイの詰まりどころはほぼ既出。
